# UI 保证层：让"产出好看"变成管线里的机械保证

> 结论先行：**AI 团队产出的东西丑，不是因为模型不会写，而是因为我们把"审美"交给了模型的自觉。**
> 提示词里写"容器 1200px、禁 emoji、圆角统一"是**建议**，模型遵守率不稳；可交付质量必须做成**管线里的机械保证**——和当初修「原型完全不能看」用 `sanitizeHtml` + `webtest` 断言是同一个道理。

---

## 一、诊断：问题到底出在哪（有数据）

对 4 份历史产出做硬指标量测（都是真实浏览器里量的）：

| 产出 | CSS 变量 | 字号种类 | 圆角取值 | 内容列占视口 | emoji 当图标 |
|---|---|---|---|---|---|
| `yqnt` | 16 | 10 | 999/7/6/16 | **47%** ❌ | 无 |
| `q1mt` | 37 | 12 | 10/6/2/9 | **60%** ❌ | 无 |
| `694m` | 31 | 10 | 9/999/5/26/8 | 80% | 无 |
| `el3u` | 32 | 5 | **完全没有** | **63%** ❌ | **3 处** ❌ |
| `2sxj` | 32 | 11 | 4 种 | 93% | 无 |

三个真问题：
1. **内容列只有视口的 47%–63%** → 桌面浏览器里就是"中间一根窄柱 + 两侧大片空白"。**这正是用户最反感的版式**，也是最扎眼的一条。
2. **字号 5–12 级、圆角 2–5 种随手值**（5px/9px/26px 混用）→ 视觉不成体系。
3. **emoji 当图标**（提示词明令禁止，模型仍然犯）→ 观感廉价。

根因：**提示词只提供"建议清单"，没有任何机械约束**。

---

## 二、方案：三层保证（全部确定性，零 LLM）

### 第 1 层 · `engine/uikit.js`（落盘即注入，跑不掉）
- **强制设计系统**：`--pt-*` 令牌（色板 / 间距 4·8·12·16·24·32·48·64 / 字阶 / 圆角 / 阴影）+ 组件库（`pt-wrap` `pt-section` `pt-card` `pt-btn` `pt-hero` `pt-badge` `pt-grid` `pt-input` `pt-table` `pt-empty` `pt-avatar` `pt-stat` …），并自带 `prefers-color-scheme:dark`
- **注入顺序**：设计系统在前、模型自己的样式在后 → 模型仍可覆盖细节，但**底色/字体/骨架先是对的**
- **机械修正（normalizeCss）**：
  - 圆角 → 归到 `0/6/8/12/16/999`
  - 字号 → 归到字阶（消除 13.5px、15.5px、17px、22px 这类随手值）
  - **页面级容器过窄 → 提到 `var(--pt-max,1200px)`**；同时支持 `--container:620px` 这种「变量型容器」（模型常用写法，第一版漏掉了，已补）
  - 正文文本列（`.prose/.desc/.lead` 等）**不撑宽**，避免把 62ch 的阅读列拉成 1200
  - 缺 `viewport` meta 自动补
- 挂载点：`workspace.writeArtifact()` —— **所有 `.html` 产出落盘时无条件过这一层**

### 第 2 层 · `engine/designaudit.js`（把"丑"量成分数）
真浏览器（1440×900）量 8 类指标并打分（0-100）：

| 指标 | 判据 |
|---|---|
| 内容列占比 | <62% 扣 22（严重）· <75% 扣 8 |
| 字号层级 | <4 级扣 10 · >10 级扣 8 |
| 圆角一致性 | >4 种扣 8 |
| 文字对比度 | <3 扣 16 · <4.5 扣 7 |
| 交互反馈 | hover 规则 <3 扣 8 · transition <4 扣 6 |
| 阴影层次 | <2 扣 5 |
| 内容密度 | <600 字扣 14（空壳感）· 页高 <1.2 屏扣 8 |
| 硬伤 | 横向溢出扣 12 · emoji 图标扣 5 · 缺 viewport 扣 6 · 字体栈不对扣 6 |

**并且会自我治疗**：低对比度文字（如 `rgb(138,147,141)` 压在 `rgb(238,241,239)` 上 = 1.61:1）→ 自动算出达标色（≥4.5:1）→ 注入 `#pt-fix` 落盘。

### 第 3 层 · 编排里的闭环（`orchestrator.js`）
原型产出后自动跑：
1. 审计 → 事件流写入 `design` 事件（分数/等级/问题清单/自动修正项）+ 消息面板播报
2. **分数 < 78 且有中/严重问题 → 带着"审计问题清单"让编码角色重做一轮**（提示词里给出硬性六条：容器 1200 / 字阶 / 圆角四种 / 对比度 ≥4.5 / hover / 禁 emoji）
3. 复测：**设计分必须涨、且浏览器测试仍通过**才采纳；否则**自动回滚到原版**（复用视觉打磨那套事务性回滚思想）

## 三、效果（同一批产出，前后对照）

| 产出 | 分数 | 内容列占比 | 对比度 | 自动修正项 |
|---|---|---|---|---|
| `yqnt` | **40 → 86**（+46） | 47% → **83%** | 1.61 → **4.78** | 8 |
| `q1mt` | **62 → 100**（+38） | 60% → **78%** | 2.55 → **4.95** | 12 |
| `694m` | **70 → 94**（+24） | 80% → 80% | 2.12 → **4.58** | 10 |
| `el3u` | **54 → 78**（+24） | 63% → **80%** | 2.07 → **4.95** | 3 |
| `2sxj` | **76 → 100**（+24） | 93% → 93% | 2.07 → **4.93** | 14 |

**平均 60.4 → 91.6 分（+31.2）**，全部来自机械修正，**没有花一次 LLM 调用**。

肉眼验收（识图）：
- 修复前：「内容集中在页面中间一条较窄的柱子里，左右两侧有大片空白」
- 修复后：「结构清晰、视觉和谐、交互合理，完全具备作为正式产品的潜力」

> 之所以这层能"特别有效"：**它修的是模型最不稳定的那部分（版式参数），而不是替它做创意。**
> 模型擅长写文案、写交互逻辑、写业务规则；它不擅长记住"容器 1200、圆角只有四种"这种事——那就交给代码记住。

## 四、怎么验证 / 回归

```bash
# 对历史产出跑「审计 → 注入 → 再审计」，出前后对照表 + 对比截图
node tools/audit-prototypes.mjs
# 指定某几次运行
node tools/audit-prototypes.mjs run-20261006165957-yqnt
```
产物：`doc/uikit-demo/<runId>/{before,after}.html`、`doc/uikit-demo/对比-{before,after}.png`

## 五、相关文件
- `engine/uikit.js` — 设计系统 + 机械修正 + 注入
- `engine/designaudit.js` — 量化审计 + 打分 + 对比度自愈
- `engine/workspace.js` — `writeArtifact()` 里无条件过 UI 保证层
- `engine/orchestrator.js` — 审计闭环：不达标带问题重做一轮，改坏回滚
- `engine/roles/dev.prompt.md` — 编码角色的 UI 契约（用 `pt-` 组件类、容器 1200、字阶、圆角四种、禁 emoji）
- `tools/audit-prototypes.mjs` — 回归/演示脚本
